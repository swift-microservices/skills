# Shapes: the monolith, microservices, and the transport

Use this reference when deciding what a system is deployed as and how it is reached, and when a module may have earned its own service. Every system on the swift-microservices packages is modular; the shape decides how many processes the modules run in, and the transport decides how callers reach them. The two are independent choices.

## Two axes, chosen per system

**Deployment shape.** A *monolith* is one package and one executable with every module inside. *Microservices* are one package per module, each its own executable and its own database. The monolith is not a compromise or a stepping stone: it is the smallest architecture that fits, and for most products it is the final one. Split only when a module has earned it (see below).

**Transport.** *HTTP* on Hummingbird or Vapor, *gRPC* on grpc-swift, or *both*. Any transport goes with any shape:

| | HTTP | gRPC | Both |
| --- | --- | --- | --- |
| **Monolith** | a web or mobile product with one backend | apps and other systems that speak gRPC, no browser | browsers on HTTP, apps or partners on gRPC |
| **Microservices** | services fronted by an HTTP gateway (the usual pair) | services reached by gRPC clients directly, plus internal RPC | a gateway for browsers, gRPC for apps and between services |

Choose the shape from ownership, release, scaling, security, and failure isolation; choose the transport from who calls. Neither choice changes the rules inside a module, so a system can change either later by moving targets, not by rewriting them.

## The module

The module is the unit of the architecture in both shapes: one bounded capability with its own Core and Postgres targets, its own use cases with the caller in their signature, its own tables, its own migrations. In microservices a module *is* a service; the grammar substitutes `<Service>` for `<Module>` and nothing else changes.

| Target | Monolith | Microservice |
| --- | --- | --- |
| Core | `<Module>Core` (`CatalogCore`, `UsersCore`) | `<Service>Core` |
| Postgres | `<Module>Postgres` | `<Service>Postgres` |
| Provider adapter | `<Module><Technology>` (`UsersBcrypt`) | `<Service><Technology>` |
| Temporal | `<Module>Workflows` | `<Service>Workflows` |
| HTTP transport | `<Module>HTTP` | `<Service>HTTP` |
| gRPC transport | `<Module>GRPC` | `<Service>GRPC` |
| Executable | `<Project>`, one, composing every module | `<Service>` |
| Package | `<organization>-<project>` (`acme-backend`) | `<organization>-<service>` |

Transport targets are per module in both shapes. A gRPC monolith has `CatalogGRPC`, `UsersGRPC`, … and one executable registering every module's services on one server; an HTTP monolith has `CatalogHTTP`, `UsersHTTP`, … and one executable mounting every module's controllers on one router. That is what keeps a module movable: turning it into a service moves its targets into their own package and changes only the composition root.

A module never imports another module's Core, Postgres, or transport target. Only the composition root sees more than one module. The building-swift-services skill owns the layout inside a module; this reference owns what sits between modules.

## The monolith

One package, one executable, every module inside, one composition root that constructs each module's database, use cases, and transport and owns them in one `ServiceGroup`.

Modules talk through use-case protocols. A consumer module declares in its own Core the protocol it needs (`XUseCaseProtocol`, or a narrow client port with only the operations it calls); the composition root injects the producer module's use case. The call is local, but it is still a call across an ownership boundary: a transaction never spans it, the producer's use case decides authorization against the caller it is handed, and the consumer stores what the producer returns rather than reaching into its tables. Design a cross-module call exactly as you would a remote one, minus the network.

Dependency direction between modules is drawn and cycles are rejected, the same as between services. Break a cycle by reconsidering ownership, extracting a third module, or turning one direction into a fact the other module reacts to.

Because the executable is the deployment unit, the monolith has one image, one configuration, one set of key files, and one process identity. A Temporal worker, when a module needs one, is `worker run` on the same executable, composing the modules that have Activities.

## One database, many modules

A monolith owns one database, and each module owns its tables inside it: unqualified table names, one create migration per table, identifiers generated by the database with `UUID DEFAULT uuidv7()`. Between modules the ownership rules are the ones between services, enforced by review rather than by a network: no cross-module join, no cross-module foreign key, no query on another module's tables, no identifier generated for another module. A module that needs another module's data asks that module's use case.

Roles are per process, so the monolith has one set: `<project>_service`, created by `CreateServiceRole` as the first migration; `<project>_internal`, created by `CreateInternalRole`, when any module has tenant tables; `<project>_worker` with Temporal. Each module's Postgres target exposes its migrations as an ordered list; the composition root registers the role migrations first, then every module's list in module dependency order, and runs them at boot behind `serve --migrate-database`.

Row-level security is the same in both shapes, and its main concern is tenant isolation: the policy on a table whose rows belong to users is `user_id = NULLIF(current_setting('app.caller_user_id', true), '')::uuid`, what the caller may do stays in the use case, and the internal role has its own `USING (true)` policy. Scopes are per role per module (`PostgresCatalogScope`, `PostgresCatalogInternalScope`), so which scope adopts a use case's scope protocol decides which database the use case may run on.

## The transport

**HTTP** is for browsers, mobile apps that speak REST, and anything that expects OpenAPI. In a monolith it lives in the `<Module>HTTP` targets, one router in the executable; in microservices it is the gateway package, `<organization>-api`, which owns no data and translates each request into an RPC. Either way the surface identifies the caller once with `BearerAuthenticationMiddleware`, requires per tier, and answers failures as RFC 9457 problem details.

**gRPC** is for apps and systems that speak it and for every internal call between services. In a monolith the `<Module>GRPC` targets register their services on one `GRPCServer`; in microservices each service has its own. Contracts are split by audience (`<Entity>PublicService`, `<Entity>Service`, `<Entity>InternalService`) so that identification applies per service, never per method; in a monolith the internal audience usually does not exist, because no process calls in.

**Both** means both surfaces over the same use cases: the module's HTTP controllers and its gRPC conformances call the same `XUseCaseProtocol`, and no business decision lives in either transport.

Publish nothing but the edge. Internal gRPC ports stay off the ingress; public TLS terminates at the ingress or the gateway.

## Where identity is verified

A user is proved by a token, a process by its certificate, and the use case decides what either may do. Where the token is verified depends on the shape:

- **Monolith:** once, at the transport, because no process boundary is crossed. The HTTP middleware or the gRPC interceptor verifies the token with the issuer's public key and binds the caller; the tenant setting is bound beside it; every use case in every module reads the same bound caller.
- **Microservices:** at every process that receives it. The gateway verifies; each service verifies again with the same public key; the token crosses a boundary only as the original bearer credential, forwarded by `BearerPropagationInterceptor<UserIdentity>` on user-service descriptors alone. No process trusts an identity a caller asserts, and no process mints a credential on a user's behalf. Processes prove themselves to each other by certificate over mTLS from the stack's CA.

Authorization is placed in the use case in both shapes. A policy, an interceptor, a middleware, and a gateway identify; they never decide.

## When a module becomes a service

A module has earned its own service when at least one of these is concrete, measured, or mandated, and not before:

- it must scale, or be placed, independently of the rest;
- it must release on its own cadence, or be owned by a team that ships alone;
- its failure must not take the rest down, or the rest's failure must not take it down;
- it holds data under a compliance boundary the rest must not enter;
- it must be reached by a process the monolith does not front.

"It is a separate concept" is not a reason; the module boundary already gives that. One service per entity, table, endpoint, or team name is not a boundary.

Turning a module into a service is three moves, not a program. Release its contract in `<project>-protos`, split by audience. Give the module its own package, database, executable, and role migrations, keeping its Core and Postgres targets as they are. In the consumer, keep the use-case protocol and swap the injected implementation for a gRPC client adapter conforming to the same protocol, constructed in the consumer's composition root over mTLS with the propagating interceptor. What the consumer calls does not change; what answers does. Moving existing rows into the new database, and removing them from the old one, is the user's decision, planned and executed explicitly.

## The decision record

Write the shape down once, at the start, in the design:

```text
shape: monolith | microservices
transport: HTTP | gRPC | both
modules: <name> owns <tables>, exposes <use cases | proto services>
callers: browsers | apps (REST | gRPC) | partners | internal processes
identity: verified at <the transport | the gateway and every service>
split candidates: <module>: <the concrete reason>, or none
```

Revisit it when a split candidate's reason becomes real, and only then.

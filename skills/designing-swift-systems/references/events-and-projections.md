# Events and projections

Use this reference when an interaction is a fact rather than a request: something happened in one module, other modules react to it, and the producer needs no answer. It applies in both shapes. The mechanism is the same in a monolith and across services; what differs is the publisher the composition root injects.

## When an event is the mechanism

An event fits when all three hold:

- the producer's use case is complete once its own transaction commits, and it needs nothing back;
- more than one consumer reacts, or one consumer whose effect must survive the producer's crash and its own;
- the consumer may lag: the design tolerates the fact arriving later, twice, or out of order with an unrelated fact.

If the producer needs a result, it is a use-case call (monolith) or gRPC (microservices). If the reaction is a multi-step process with retries, timers, or waits, it is a workflow (the orchestrating-temporal-workflows skill). If only one consumer exists and it may run inside the producer's transaction, it is a direct call; the outbox appears the day that stops being true.

## The event

An event is an immutable `Sendable` value in the producer's Core, named as a past-tense fact (`OrderPlaced`, `SubscriptionExpired`), carrying:

- `eventId: UUID`, generated by the producer's database when the outbox row is written, so consumers deduplicate on it;
- the owning entity's identifier and the facts a consumer needs to react, not the entity;
- `occurrenceDate`, stamped by the database.

It carries no credential and no derived decision. A consumer that needs more than the event holds asks the owner's use case with the identifier, under its own caller.

Across services the wire form is a protobuf message in `<project>-protos`, versioned additively like an RPC. In a monolith the Swift value is the wire form.

## The transactional outbox

The producer never publishes from inside a use case, and never publishes after commit from memory: the first loses the fact when the broker is down, the second loses it when the process dies between commit and publish. The fact is written where the mutation is written:

```sql
CREATE TABLE outbox (
    id UUID PRIMARY KEY DEFAULT uuidv7(),
    topic TEXT NOT NULL,
    payload JSONB NOT NULL,
    creation_date TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    publication_date TIMESTAMPTZ
);
CREATE INDEX outbox_pending ON outbox (creation_date) WHERE publication_date IS NULL;
```

The use case calls its `XEventPublisher` port inside `withTransaction`; the Postgres implementation inserts the outbox row in the same transaction as the mutation, so the fact exists exactly when the mutation does. A relay in the producer's process, owned by its `ServiceGroup`, reads pending rows in order, hands each to the broker adapter, and stamps `publication_date` on success. The relay retries with backoff and never deletes; retention prunes published rows later.

Delivery is at least once. A row can be published, then the stamp can fail, and the row is published again. That is the contract every consumer is written against.

## The consumer

A consumer is a use case in the consuming module, reached through a port the adapter calls, with the event in its signature and the process as its caller:

```swift
package protocol ReactToOrderPlacedUseCaseProtocol: Sendable {
    func callAsFunction(event: OrderPlaced) async throws(ReactToOrderPlacedUseCaseError)
}
```

It is idempotent by event id. The first statement of its transaction records the id in a consumer-owned table with a unique constraint (`processed_events (event_id, consumer)`), and a duplicate insert ends the transaction as a no-op success. Everything the consumer writes happens in that same transaction, so a crash after the insert rolls the id back and the redelivery is processed once.

A consumer does not assume order across topics. Where order within a topic matters, the broker adapter delivers one partition at a time and the consumer checks the entity's version in its `WHERE` clause, treating a stale event as already applied.

A consumer's failure is its own. It retries transient errors with bounded attempts; a permanent failure parks the event for a person, logged with the event id, never blocking the topic for everyone else.

## The projection

A projection is a read model the consumer owns, built from events, for a read the owner cannot serve at the needed latency or shape: a listing that joins facts from two modules, a count, a denormalized page.

- It is written by idempotent upsert keyed on the owning entity's identifier, guarded by the event's occurrence date or the entity's version so a late event does not regress it.
- It is rebuildable: the owner exposes a way to replay or re-read its current state (a paged internal RPC, or the module's use case in a monolith), and rebuilding is a documented operation, not an emergency.
- It is never a source of truth. A decision reads the owner; a page reads the projection. A use case that would decide from a projection is asking the wrong module.
- It lives in the consumer's Postgres target under the consumer's tables and its tenant policies apply to it like any other table.

## What not to do

- No broker before a second consumer exists, and no topic before a producer has a fact someone reacts to. Infrastructure is added from an interaction in the design, never from the shape.
- No exactly-once claim, anywhere. Deduplication is the consumer's, by event id, in its own transaction.
- No reading another module's tables to build a projection; it is built from the owner's events and the owner's use case, or it does not exist.
- No workflow history as an outbox and no outbox as a workflow: an event is a fact, a workflow is a process.
- No decision in the event. `OrderPlaced` says what happened; whether to send an email is the consumer's use case, against its own policy.
- No credential in the event and no impersonation in the consumer: the consumer runs as its process, through its internal role, and names the user in its `WHERE` clause when a row belongs to one.

## The module grammar

| Piece | Lives in | Name |
| --- | --- | --- |
| The event value | producer's `<Module>Core` | `OrderPlaced` |
| The publisher port | producer's `<Module>Core` | `OrderEventPublisher` (`publish(_:)`, called inside `withTransaction`) |
| The outbox table and its statements | producer's `<Module>Postgres` | `outbox`, `EnqueueOutboxStatement`, `PostgresOrderEventPublisher` |
| The relay | producer's executable, owned by the `ServiceGroup` | `OutboxRelay` |
| The broker adapter | a `<Module><Technology>` target | `OrderNATSPublisher`, `OrderKafkaPublisher` |
| The consumer use case and its port | consumer's `<Module>Core` | `ReactToOrderPlacedUseCase` |
| The processed-events table and the projection | consumer's `<Module>Postgres` | `processed_events`, the projection table |
| The subscription | consumer's `<Module><Technology>` target and its executable | `OrderPlacedSubscription` |

The building-swift-services skill owns the layout inside each target; this table says only what goes where.

## In a monolith

The composition root is the broker by default. It builds the producer's publisher over the outbox and a relay that delivers to the consumers' use cases in-process, in order, with the same at-least-once contract and the same processed-events dedup. That keeps the consumer's code identical to the microservices version, so moving either module out later swaps the relay's target for a broker adapter and nothing else. Skip the outbox only when the single consumer's effect need not survive a crash and the design says so; then the producer's use case calls the consumer's use case directly, in its own transaction, and there is no event.

## The consistency record

Every event edge is written into the design's consistency record like any cross-module interaction:

```text
fact: OrderPlaced, owner: Orders
consumers: Billing (charge), Notifications (email)
staleness: seconds; a page may lag, a decision never reads the projection
duplicates: by eventId in processed_events, per consumer
ordering: per order id; a stale event is applied as no-op by version check
failure: consumer retries with backoff; a permanent failure parks the event, logged
rebuild: Orders.ListOrdersInternalService, paged
```

PASS if the design states the deployment shape it recommends and why, cuts the system into a small number of modules or services each built around one capability (for example listings, orders, payments, notifications, with buyers and sellers as users rather than as modules), states which module or service owns which data with no table read by two of them and identifiers generated by the owning database, reserves events or a durable workflow for order-event fan-out and the multi-step payment/payout process with a stated reason, and records for each cross-module or cross-service interaction whether consistency is strong or eventual and how duplicates and failures are handled. If it recommends microservices, it names the module whose concrete reason earns a separate process and uses gRPC for the synchronous calls; if it recommends a monolith, modules call each other through use-case protocols injected in the composition root over one database with per-module tables.
FAIL if modules or services are cut per entity or per table without justification, if microservices are proposed with no module having a stated concrete reason to run alone, if two services share a database or modules join across each other's tables, if a distributed transaction is proposed, if a message broker or workflow engine is introduced with no stated requirement, or if consistency is left unstated for cross-boundary writes.
